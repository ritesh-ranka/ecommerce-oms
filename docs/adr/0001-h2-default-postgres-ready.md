# ADR-0001: Default to in-memory H2, stay PostgreSQL-ready

**Status:** accepted · **Date:** 2026-09-26

## Context

The brief allows any database and excludes containerisation. A reviewer will clone the repository and want to
run it. Two competing goals: the project should start with no setup, and the design should not quietly depend
on a toy database.

## Options

**A — PostgreSQL only.** Realistic, but the reviewer must install and configure a server first.

**B — H2 only, Hibernate-generated schema.** Fastest to write, but the schema exists nowhere reviewable and the
locking behaviour proves nothing about production.

**C — H2 in PostgreSQL-compatibility mode by default, PostgreSQL behind a profile,** with one Flyway schema
shared by both.

## Decision

**C.**

```bash
mvn spring-boot:run                                            # H2, zero setup
mvn spring-boot:run -Dspring-boot.run.profiles=postgres        # same code, same schema
```

## Why

**Against A.** `mvn spring-boot:run` working on a clean machine is worth a lot when the deliverable is read by
someone else. Anything between clone and running is friction that competes with the parts worth their attention.

**Against B.** This project's central claim is that overselling is impossible under concurrency, and that claim
rests on `SELECT … FOR UPDATE` semantics. A setup where the schema is invented by Hibernate at startup and the
locking is never exercised against a production dialect does not support the claim. Three things keep option C
honest:

**Flyway owns the schema, with `ddl-auto: validate`.** Hibernate compares every entity mapping against the
migration-built schema at startup and refuses to boot on a mismatch. Both dialects are therefore held to the
*same* schema, and drift is a startup failure rather than a runtime surprise on a rarely-used column.
`SchemaAndContextTest` turns that into a one-line assertion.

**Migrations are hand-written vendor-neutral SQL.** `BIGINT GENERATED BY DEFAULT AS IDENTITY`, plain
`DECIMAL`/`VARCHAR`/`TIMESTAMP`, no dialect-specific functions. This has a real cost — `discounts.value` had to
be renamed `discount_value` because `VALUE` is reserved in H2 — and that cost is the point: the constraint is
being enforced, not assumed.

**H2 runs in `MODE=PostgreSQL`,** and all locking goes through JPA `LockModeType`, which both dialects render
natively. The pessimistic locking the oversell guarantee depends on is the same mechanism in both.

**Correctness is not left to the dialect anyway.** The `CHECK (reserved >= 0 AND on_hand >= 0 AND reserved <=
on_hand)` constraint is plain SQL enforced identically by both, so the backstop on the oversell invariant does
not vary with the deployment target.

## Consequences

**Accepted costs**

- No hand-written SQL convenience: no `ON CONFLICT`, no `RETURNING`, no JSONB. Where a JSON column would have
  been natural (outbox payloads) the schema uses `VARCHAR(4000)` with a length check at write time.
- Every schema change costs a migration file. No `hbm2ddl` shortcut, including in tests.
- H2 is not a production database. Connection-pool behaviour, planner decisions, and lock contention at scale
  would all need verifying against PostgreSQL before any real deployment.
- Data is lost on restart by default, which is correct for a demo and wrong for anything else.

**Gains**

- Clone, `mvn spring-boot:run`, and the seeded catalog is browsable — including a SKU stocked with exactly one
  unit so the oversell demo is immediately runnable.
- The full test suite, concurrency test included, runs with no external service.
- The PostgreSQL switch is a profile flag rather than a project, because the constraint was enforced
  throughout rather than retrofitted.

## Verification

`SchemaAndContextTest` boots the context under `ddl-auto: validate`, which is a complete check that the
migrations and every entity mapping agree. All 34 integration tests, including `OversellPreventionIT`, run
against the Flyway-built schema — the real one, not a generated approximation.
